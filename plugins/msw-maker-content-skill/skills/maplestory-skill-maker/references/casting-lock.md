# Casting Input & Animation Lock

Attacker-side input handling, movement lock, and animation-end detection during a skill cast — independent of the damage/judgment logic in [targeting-judgment.md](targeting-judgment.md). This lives entirely on the per-player Player Adapter Component (see [skill-framework.md](skill-framework.md)) — the damage/judgment logic it's independent of runs in the Registry Logic. See [../SKILL.md](../SKILL.md) for the Domain Reference Files index.

The lock state below is generic (`CastingLockActive`/`CastingSkillKey`), not one flag per skill key. Anywhere `<Skill>LockActive` or `<Skill>AnimationKey` appears below, read `<Skill>` as resolved through `CastingSkillKey` and the Registry Logic's skill-data lookup for that key's `animationKey` — see [skill-framework.md](skill-framework.md)'s Casting State Ownership section for why this is a single pair of properties, not one pair per skill.

## Player Casting Input & Animation-End Lock Rule (required for every skill)

These are the foundational **Animation Execution Principles** for every attack skill in this project:

1. **Absolute Physics Integrity (No Floating/Freezing)**:
   - NEVER use heavy-handed C++ disabling hacks like `PlayerControllerComponent.Enable = false` or rigid full-vector zeroing like `body.MoveVelocity = Vector2.zero` / `InputSpeed = 0` on the player. Disabling the controller or zeroing the full velocity vector freezes the gravity/falling physics entirely, causing players to hover or stop unnaturally in mid-air.
   - To freeze horizontal movement and prevent sliding drift, ONLY clear the horizontal velocity component: **`body.MoveVelocity = Vector2(0, body.MoveVelocity.y)`** locally on the client. Keep `playerController.Enable = true` and `InputSpeed` at default values so native gravity and falling continue 100% naturally in mid-air.
   - This principle only covers *velocity* (movement). It does NOT stop the character from *turning in place* — see principle 9 for the separate facing-lock mechanism.

2. **Native State Machine Integration**:
   - The engine's built-in `"ATTACK"` state natively blocks horizontal movement and turning with zero latency, while leaving vertical falling/gravity active. It also natively prevents landing transitions from cutting the attack animation short.
   - `data.animationKey` (where `data = _AttackSkillLogic:GetSkillData(self.CastingSkillKey)`) dispatches to one of two animation control paths, decided automatically by `PlayerAttack:IsNativeBodyActionState(animationKey)` — no per-skill branching needed by the skill author:
     - **Native body-action name** (one of the 14 `MapleAvatarBodyActionState` values — `stand`/`walk`/`attack`/`hit`/`crouch`/`fall`/`rope`/`ladder`/`dead`/`sit`/`heal`/`alert`/`fly`/`blink`, see `msw-avatar`): map `"ATTACK"` to it via `asac:SetActionSheet("ATTACK", animationKey)`, then `ChangeState("ATTACK")` on the server. This is the **default** — if a skill's data doesn't set `animationKey` at all (`nil`/`""`), `RequestUseSkill` falls back to `"attack"` and takes this path.
     - **Custom action id** (anything outside those 14 names, e.g. a specific skill's own clip name like `"CustomSlash"`): call `asac:RemoveActionSheet("ATTACK")` instead of `SetActionSheet`, then drive the clip once via a Server→Client RPC (`PlayCastAnimation` → `NotifyPlayCastAnimation`) that builds an `ActionStateChangedEvent(actionName, actionName, 1, SpriteAnimClipPlayType.Onetime)` and `SendEvent`s it to `AvatarRendererComponent:GetBodyEntity()`. Required because `AvatarStateAnimationComponent` continuously re-applies whatever is mapped to `"ATTACK"` every tick the state stays `"ATTACK"` — harmless for a native pose (re-asserting the same recognized state is how looping poses already work) but it stomps a one-shot custom clip after its first frame (see principle 7). Keeping the `"ATTACK"` mapping in place while also firing the one-shot event is the bug, not a variant to preserve — the mapping must be removed for this path.
   - Look the key up through `CastingSkillKey` — do not hardcode a skill-specific animation key property on `PlayerAttack`. Confirmed: a `@Logic` is reached the same way as a `@Service` — the plain global accessor `_<ExactScriptName>` (`AttackSkillLogic.mlua` → `_AttackSkillLogic`), per `msw-scripting/SKILL.md` §3.2. No lookup service call is needed.
   - Restore `"ATTACK"` back to `"attack"` and state to `"IDLE"` upon animation completion — the animation-end detection in principle 4 below is unaffected by which of the two paths played the clip, since both ultimately trigger a real `SpriteAnimPlayerEndEvent` on the body entity.
   - Reference implementation: `RootDesk/MyDesk/PlayerAttack.mlua` — `RequestUseSkill` (dispatch) + `IsNativeBodyActionState` (classification) + `PlayCastAnimation`/`NotifyPlayCastAnimation` (custom-action RPC pair).

3. **Zero-Latency Client-Side Input Gating**:
   - Track casting lock authoritatively via a single `@Sync property boolean CastingLockActive` plus `property string CastingSkillKey` pair on `PlayerAttack` — not one lock flag per skill key (see [skill-framework.md](skill-framework.md)'s Casting State Ownership).
   - Instantly set `self.CastingLockActive = true` and `self.CastingSkillKey = skillKey` locally on the client in the key-down handler to prevent multiple overlapping casts or key-hold walk overrides before the server's sync message arrives.

4. **Zero-Latency Native Animation-End Detection**:
   - To unlock player input, subscribe to `"SpriteAnimPlayerEndEvent"` on the player avatar's body entity (obtained via `AvatarRendererComponent:GetBodyEntity()`). This event is raised natively by the rendering player when the entire animation playback is 100% completed (including the delay of the final frame), dynamically adjusting to any clip length or PlayRate.
   - Unsubscribe from `"SpriteAnimPlayerEndEvent"`, locally restore movement properties, and send server RPC `RequestReleaseCastingLock()` to set `self.CastingLockActive = false` and `self.CastingSkillKey = ""`.

5. **Flinch & Hit Interruption Immunity**:
   - To prevent taking damage (flinching) from cutting the skill animation short, make the player immune to hits during the `CastingLockActive` casting window inside `PlayerHit.mlua`'s `IsHitTarget()` by returning `false` (obtained via `self.Entity.PlayerAttack` dot access, or `self.Entity:GetComponent("script.PlayerAttack")`). This completely blocks the `"HIT"` state transition natively. This check is a single flag read regardless of which skill is casting — no per-skill branching needed.

6. **Interrupted Cast Recovery (required)**:
   - Bug: principle 2's "ATTACK natively blocks horizontal movement" is not an absolute guarantee against every state interruption — vertical movement (falling off a ledge, knockback, a foothold edge) can still force `StateComponent` out of `"ATTACK"` into another state (`FALL`, `HIT`, `MOVE`, ...) **before** the attack clip's own `SpriteAnimPlayerEndEvent` ever fires. When that happens, principle 4's animation-end listener never runs, so `CastingLockActive` never gets released — the player is permanently unable to cast again (looks like "cooldown stuck forever" from the player's perspective) and, per principle 5, permanently hit-immune.
   - Fix, client side: also subscribe to the native `StateChangeEvent` on `self.Entity` (`self.Entity:ConnectEvent(StateChangeEvent, self.OnStateChanged)`, disconnected in `OnEndPlay`). If `CastingLockActive` is true and `event.PrevStateName == "ATTACK"` and `event.CurrentStateName ~= "ATTACK"`, run the exact same release path as the normal animation-end case (disconnect the `SpriteAnimPlayerEndEvent` handler, clear `CastingLockActive`/`CastingSkillKey` locally, call `RequestReleaseCastingLock()`). Factor the shared cleanup into one method (e.g. `ReleaseCastingLockLocally()`) so both the normal-completion path and the interrupted path stay in sync.
   - Fix, server side (defense in depth — covers client bugs/disconnects/dropped RPCs that principle 6's client-side fix can't): when `RequestUseSkill` locks casting, also schedule a `_TimerService:SetTimerOnce` safety timer (a few seconds — generous relative to any real cast animation) that force-calls `RequestReleaseCastingLock()` if `CastingLockActive` is still `true` for that same `CastingSkillKey` once it fires. Clear this timer whenever `RequestReleaseCastingLock()` runs normally, and re-arm it on every new `RequestUseSkill` call, so it never fires during a legitimate cast.
   - Reference implementation: `RootDesk/MyDesk/PlayerAttack.mlua` — `OnStateChanged`/`ReleaseCastingLockLocally` (client) + `CastingSafetyTimerId`/`ForceReleaseIfStuck` (server).

7. **Custom Cast Animation Cutoff (required)**:
   - Bug: with only principle 2's original single-path behavior (`SetActionSheet("ATTACK", data.animationKey)` unconditionally, then `ChangeState("ATTACK")`), a custom `animationKey` outside the 14 `MapleAvatarBodyActionState` names played its first frame correctly and then reverted — not because any project script re-triggered anything, but because native `AvatarStateAnimationComponent` continuously re-applies whatever `"ATTACK"` is currently mapped to for as long as the state stays `"ATTACK"`. For a recognized native pose this re-apply is a no-op (same clip keeps playing); for an arbitrary custom id it has no matching clip to resolve, so the state's own animation resets. Symptom matches `msw-avatar`'s documented "Auto playback ↔ manual ActionStateChangedEvent collision" pitfall exactly — first frame shows, then gets stomped.
   - Fix: classify `animationKey` first (`IsNativeBodyActionState`, principle 2's two-path split above). Only call `SetActionSheet` for a native pose. For a custom id, `RemoveActionSheet("ATTACK")` so nothing keeps re-asserting a mapping, then fire the clip once via `ActionStateChangedEvent` sent directly to the body entity — a one-shot event that native re-apply logic has nothing to fight, since there is no longer an `"ATTACK"` mapping to keep reapplying.
   - Do not try to fix this by re-adding the `SetActionSheet` call "just to be safe" alongside the one-shot event — that reintroduces the exact collision this fix removes.
   - Reference implementation: `RootDesk/MyDesk/PlayerAttack.mlua` — `IsNativeBodyActionState`, `PlayCastAnimation` (`ServerOnly`), `NotifyPlayCastAnimation` (`Client` RPC, mirrors the `SendCastRejected`/`NotifyCastRejected` UserId-targeting pattern from principle 6's neighbor bug fix).

8. **First-Cast Animation Race (required)**:
   - Bug: `RequestUseSkill` fires `asac:RemoveActionSheet("ATTACK")` and `sc:ChangeState("ATTACK")` back to back in the same server call, but they reach the client through two different channels — the `@Sync` property update for `StateToAvatarBodyActionSheet`, and the `StateChangeEvent` dispatch. On a fresh player entity, nothing has ever called `RemoveActionSheet` before, so on the *very first* cast there's a real race: if `StateChangeEvent` arrives at the client before the removal's `@Sync` update lands, `AvatarStateAnimationComponent.ReceiveStateChangeEvent` still resolves the untouched default `"ATTACK" → "attack"` mapping and plays the native pose — stomping the one-shot custom clip from `NotifyPlayCastAnimation` exactly like principle 7's bug, just triggered by a *stale* mapping instead of an *active* one. Every cast after the first is unaffected, because the removal already landed well before the first cast ever needed it.
   - Fix: don't wait for the first cast to remove the mapping — remove it once at spawn time, long before any keypress is physically possible, so the `@Sync` has ample time to land. `PlayerAttack.OnBeginPlay` (client) calls a new `@ExecSpace("Server")` method, `RequestPrewarmAttackAnimations()`, which loops every bound `SkillSlots` entry, resolves each skill's `animationKey` (with the same `nil`/`""` → `"attack"` fallback as `RequestUseSkill`), and calls `asac:RemoveActionSheet("ATTACK")` for any entry that resolves to a custom (non-native) action. `RequestUseSkill`'s own removal call stays in place too — it's now just a harmless no-op for casts after the first, and it's still what makes each cast idempotent regardless of prewarm timing.
   - This is a spawn-time-vs-cast-time ordering fix, not a network-latency workaround — it does not add any delay to the cast itself, only moves an already-happening removal earlier.
   - Reference implementation: `RootDesk/MyDesk/PlayerAttack.mlua` — `OnBeginPlay` (calls the prewarm RPC) + `RequestPrewarmAttackAnimations` (`Server`).

9. **Facing Lock During Cast (required)**:
   - Bug: principle 1's horizontal-velocity freeze stops the character from *sliding*, but `PlayerControllerComponent` still updates facing (`LookDirectionX`) on a same-side direction-key press even while `"ATTACK"` blocks actual movement — turning in place doesn't require velocity. Meanwhile `AttackSkillLogic.OnUseNormalAttackSkill` snapshots `LookDirectionX` once, at cast time, to orient the cast effect / hit effect / hitbox (see [cast-effect-attachment.md](cast-effect-attachment.md)). A direction change during the cast desyncs the two: the character visibly turns, but the effect stays pointed the original way.
   - Fix: freeze facing itself for the cast duration using the native `PlayerControllerComponent.FixedLookAt` (`@Sync int32`, confirmed via MSW docs: "the direction of the moving animation will not change, even if the character changes direction" — `0` = free/native default, non-zero = locked, sign follows the same positive-right/negative-left convention as `LookDirectionX`). In `RequestUseSkill`, right after the `ChangeState("ATTACK")` + animation dispatch, read the caster's current `LookDirectionX` sign and write that sign into `FixedLookAt`. In `RequestReleaseCastingLock`, reset `FixedLookAt = 0` to give turning back once the cast ends (covers the normal-completion, interrupted-cast, and safety-timer release paths alike, since they all funnel through this one method).
   - **Second bug, found after the server-only version above still let direction changes through**: `RequestUseSkill`'s `FixedLookAt` write is server-side, so it only reaches the casting client after a network round trip — same class of race as principle 8, except here the window is "any direction key pressed between the cast keypress and that round trip landing," not just "the first cast of a session." `PlayerControllerComponent`/`LookDirectionX` are processed **client-side** for input responsiveness, so a same-side direction key pressed inside that window still turns the character locally before the server's lock arrives.
   - Fix: predict the facing lock on the client too, the same way principle 3 already predicts `CastingLockActive`. `OnKeyDown` calls a new `LockFacingLocally()` (`ClientOnly`) that reads `LookDirectionX`'s current sign and writes it into `FixedLookAt` **instantly**, before `RequestUseSkill` is even sent. `ReleaseCastingLockLocally` symmetrically resets `FixedLookAt = 0` locally, right alongside its existing local `CastingLockActive = false`. The server-side write/reset in `RequestUseSkill`/`RequestReleaseCastingLock` stays in place unchanged — it's what makes the lock authoritative and what syncs the correct frozen facing to *other* clients observing this caster; the client-side copy exists purely to close the input-latency window for the caster's own screen. Both converge on the same value, so there's no visible conflict between the prediction and the confirmation (same pattern as `CastingLockActive`'s existing dual-write).
   - Reference implementation: `RootDesk/MyDesk/PlayerAttack.mlua` — `LockFacingLocally` (`ClientOnly`, called from `OnKeyDown`) + `ReleaseCastingLockLocally`'s unlock block (client prediction) alongside `RequestUseSkill` (lock) + `RequestReleaseCastingLock` (unlock) (server authority), all via `self.Entity.PlayerControllerComponent.FixedLookAt`.
